A large part of this release was built during our
[Doctrine Core Team Meetup 2026 in Amsterdam](/2026/09/16/doctrine-core-team-meetup-amsterdam26.html)

lets us finish work that is hard to do over GitHub comments, and many
of the pull requests below were opened, reviewed and merged during those days.

## DBAL Types per connection with dependency injection

For as long as Doctrine has existed, DBAL types have lived in a global static
registry. You registered them with `Type::addType()`, DBAL instantiated them
with `new $class()`, and every connection in the process shared the same
types. This has two well known drawbacks:

- Custom types cannot receive dependencies. A type that needs a serializer,
  an encryption service or a clock has to reach for static state.
- Registering or overriding a type is a process-wide side effect that leaks
  between connections and between tests.

The upcoming DBAL 4.6 introduces a `TypeProvider` interface that the DBAL
`Configuration` holds per connection, implemented by an instance-based
`TypeRegistry` ([doctrine/dbal#7342](https://github.com/doctrine/dbal/pull/7342)).
ORM 3.8 now resolves all types through the type provider of the connection
instead of the static `Type` methods: in the `SqlWalker`, the hydrators, the
persisters, the paginator and the schema validator ([#12421](https://github.com/doctrine/orm/pull/12421)).

This means you can construct your types yourself and hand them to a connection:

```php
<?php

use Doctrine\DBAL\Configuration;
use Doctrine\DBAL\Types\TypeRegistry;

$configuration = new Configuration();
$configuration->setTypeProvider(new TypeRegistry([
    'encrypted_string' => new EncryptedStringType($encryptionService),
    'money' => MoneyType::class,
]));
```

The registry already contains all built-in types, and types given as a class
name are only instantiated on first use. Instead of an array, you can also pass
a service locator, so types are lazy-loaded from your DI container.

If you are using Symfony, [DoctrineBundle 3.4](https://github.com/doctrine/DoctrineBundle/releases/tag/3.4.0)
already wires this up for you with the `#[AsDbalType]` attribute
([doctrine/DoctrineBundle#2221](https://github.com/doctrine/DoctrineBundle/pull/2221)).
Types become regular, autowired services, and can be restricted to specific
connections:

```php
<?php

use Doctrine\Bundle\DoctrineBundle\Attribute\AsDbalType;
use Doctrine\DBAL\Types\Type;

#[AsDbalType(name: 'encrypted_string', connection: 'default')]
final class EncryptedStringType extends Type
{
    public function __construct(private EncryptionService $encryption)
    {
    }

    // ...
}
```

With DBAL versions before 4.6 everything keeps working as before: the ORM falls
back to the global type registry, and DoctrineBundle registers attributed types
there, without dependency injection. Once DBAL 4.6 is released, you only need
to upgrade DBAL to start injecting services into your types.

## Faster Hydration

Hydration with fetch joins is significantly faster now. Previously, the
hydrator converted every column of every row to its PHP value up front, even
when the row only repeated the data of an entity that was already hydrated.
Values are now only converted when they are actually needed, and large
collections use an object id set instead of looking up each row with
`contains()`.

The gain grows with the number of rows per parent entity. In our new
benchmark of a shopping cart with fetch joined items:

| Scenario | Before | After | Diff |
|---|---:|---:|---:|
| Root only, 10k carts | 92.8 ms | 77.6 ms | −16% |
| 1:N fetch join, 1000 carts × 10 items | 122.5 ms | 82.3 ms | −33% |
| 1:N fetch join, 100 carts × 100 items | 119.2 ms | 72.4 ms | −39% |
| 1:N fetch join, 10 carts × 1000 items | 128.7 ms | 69.7 ms | **−46%** |
| ArrayHydrator, 100 carts × 100 items | 73.9 ms | 56.1 ms | −24% |

This is a port of a patch that [Tugdual Saunier](https://github.com/tucksaun)
originally proposed in [#10035](https://github.com/doctrine/orm/pull/10035),
thank you! See [#12751](https://github.com/doctrine/orm/pull/12751) for all
the details.

As a preparation for this, the hydrator APIs no longer pass row state by
reference ([#12728](https://github.com/doctrine/orm/pull/12728)), which also
makes `toIterable()` with the array hydrator faster and use less memory. If
you have written a custom hydrator, the by-reference methods
`hydrateRowData()`, `gatherRowData()` and `gatherScalarRowData()` are now
deprecated. The [UPGRADE.md](https://github.com/doctrine/orm/blob/3.8.x/UPGRADE.md)
explains how to migrate.

We also removed quadratic array copying when expanding `Criteria` and persister
parameters ([#12734](https://github.com/doctrine/orm/pull/12734)), which
helps queries with large `IN (...)` lists and many-to-many collections filtered
with criteria.

## No more useless UPDATEs for dates and value objects

This one has been requested [since 2015](https://github.com/doctrine/orm/issues/5542).
Replacing a date or a value object with a new instance that represents the
same database value used to trigger an `UPDATE`, because the `UnitOfWork`
compared objects by identity.

Starting with 3.8, when both the old and the new value are objects, the
`UnitOfWork` converts them to their database representation with the mapped
type and compares those instead ([#12753](https://github.com/doctrine/orm/pull/12753)):

```php
<?php

$event = $entityManager->find(Event::class, 1);

// mapped as "date": only the day is stored
$event->day = new DateTimeImmutable($event->day->format('Y-m-d') . ' 14:30:00');

$entityManager->flush(); // no UPDATE is executed anymore
```

This works for all built-in date and time types and for your own custom value
object types, without having to implement any additional interface. Scalar
fields are unaffected, so there is no extra cost on the hot path.

## Custom ID generators imply the CUSTOM strategy

Declaring a custom ID generator is now enough, Doctrine infers the `CUSTOM`
strategy on its own ([#12723](https://github.com/doctrine/orm/pull/12723)):

```diff
 #[ORM\Id]
 #[ORM\Column]
-#[ORM\GeneratedValue(strategy: 'CUSTOM')]
 #[ORM\CustomIdGenerator(MyIdGenerator::class)]
 public ?int $id = null;
```

Previously, omitting the strategy silently ignored the generator and expected
an assigned ID. If you rely on that behavior, specify `NONE` explicitly.
This applies to attributes, XML mappings and the `ClassMetadataBuilder`.

## OffsetPaginator improvements

The new `OffsetPaginator` introduced in 3.7 received several improvements
based on your feedback:

- The `COUNT` query is now deferred until you call `getTotalCount()` on the
  page ([#12627](https://github.com/doctrine/orm/pull/12627)), so you don't
  pay for it when you don't display the total.
- `OffsetPaginator::getTotalCount($query)` returns the total count without
  fetching any rows ([#12657](https://github.com/doctrine/orm/pull/12657)).
- Result keys of DQL `INDEX BY` are now preserved, as they were with the
  legacy `Paginator` ([#12678](https://github.com/doctrine/orm/pull/12678)).
  If your code relies on `WindowPage::getItems()` returning a 0-based list for
  an `INDEX BY` query, wrap it in `array_values()`.

We also fixed two bugs with ordering in paginator subqueries for custom types
([#12716](https://github.com/doctrine/orm/pull/12716)) and with subselect
nesting in the `LimitSubqueryOutputWalker`
([#12715](https://github.com/doctrine/orm/pull/12715)).

## More improvements

- `EntityRepository::findBy()` and `findOneBy()` accept the `SortDirection`
  enum for `$orderBy`, like the `QueryBuilder` already does
  ([#12613](https://github.com/doctrine/orm/pull/12613)):

  ```php
  <?php

  $repository->findBy(['status' => 'open'], ['createdAt' => SortDirection::Descending]);
  ```

  If you override these methods in a custom repository and copied the
  docblock, static analysis asks you to widen the `$orderBy` type.

- DQL functions implementing `ExpressionWithReturnType` now have their result
  converted in SQL with `convertToPHPValueSQL()` of the declared type, the same
  way as a column of that type ([#12704](https://github.com/doctrine/orm/pull/12704)).
  This is the foundation for spatial DQL functions on platforms like Oracle
  and Db2.

## Schema Editor API

Schema generation can use the new DBAL schema editor API (`TableEditor`,
`SchemaEditor`, ...) instead of the mutable DBAL schema objects, which are
deprecated in DBAL. It requires DBAL 4.5 and is enabled with:

```php
<?php

$configuration->setUseSchemaEditorApi(true);
```

With DBAL 4.5 or higher installed, not using the schema editor API is now
deprecated ([#12780](https://github.com/doctrine/orm/pull/12780)), because
it will be the only option in ORM 4.0. Note that foreign keys without an explicit
name are now named by the database instead of DBAL. On MySQL this can exceed
the maximum identifier length for long table names, in which case you need
to set `foreignKeyName` on your `#[JoinColumn]` or `#[JoinTable]` mapping.

Related to this, passing custom column platform options through the `options`
of a mapping is deprecated, since DBAL 5 removes them.

## Second Level Cache requires an additional package

If you use the second level cache, you now need to install an additional
package ([#12752](https://github.com/doctrine/orm/pull/12752)):

```bash
composer require doctrine/orm-plugin-second-level-cache
```

Without it, `Configuration::setSecondLevelCacheEnabled(true)` throws an
exception. For now the package only contains a marker class, the second level cache still
lives inside the ORM.

The second level cache is a large feature that is deeply wired into the
`UnitOfWork`, and nobody on the current team is an expert on it anymore.
Before deciding whether to keep maintaining it, move it to a separate package
or remove it, we want to know how many of you are using it. The install
numbers of this package on Packagist will give us that answer.
