Today we have [released Doctrine DBAL 4.6.0](https://github.com/doctrine/dbal/releases/tag/4.6.0),
alongside [ORM 3.8.0](/2026/11/14/orm-3.8.0-released.html). As with the ORM,
most of this release was finished during our
[Doctrine Core Team Meetup 2026 in Amsterdam](/2026/09/16/doctrine-core-team-meetup-amsterdam26.html)
from November 3rd to 5th. Thank you to [Mollie](https://www.mollie.com/) for
hosting us in their offices, it was a very productive three days.

## Types per connection with dependency injection

DBAL types have always lived in a global static registry. You registered them
with `Type::addType()`, DBAL instantiated them with `new $class()`, and every
connection in the process shared them. Custom types could not receive any
dependencies, and registering or overriding a type was a process-wide side
effect that leaked between connections and tests.

With DBAL 4.6, the `Configuration` of each connection holds a `TypeProvider`
and every type is resolved through it
([#7342](https://github.com/doctrine/dbal/pull/7342)):

```php
<?php

use Doctrine\DBAL\Configuration;
use Doctrine\DBAL\DriverManager;
use Doctrine\DBAL\Types\TypeRegistry;

$configuration = new Configuration();
$configuration->setTypeProvider(new TypeRegistry([
    'encrypted_string' => new EncryptedStringType($encryptionService),
    'money' => MoneyType::class,
]));

$connection = DriverManager::getConnection($params, $configuration);
```

A `new TypeRegistry()` now already contains all built-in types, so you only
pass your own. Types given as a class name are instantiated on first use, and
instead of an array you can pass a Symfony service locator to lazy-load types
from your container.

Connections that never call `setTypeProvider()` keep using the global
registry, so existing code relying on `Type::addType()` keeps working. Be aware
that once a connection has its own provider, types registered globally are
not visible to it anymore. The static `Type` methods like `Type::getType()`
and `Type::addType()` are deprecated, DBAL 5 will not have a static type
registry at all.

The rest of the ecosystem is ready for this:

- [ORM 3.8](/2026/11/14/orm-3.8.0-released.html) resolves all types through
  the provider of the connection.
- [DoctrineBundle 3.4](https://github.com/doctrine/DoctrineBundle/releases/tag/3.4.0)
  registers types with the `#[AsDbalType]` attribute as regular, autowired
  services and builds one registry per connection.

Thank you to [Jérôme Tamarelle](https://github.com/GromNaN) for driving this
across DBAL, ORM, DoctrineBundle and MongoDB ODM.

## Up to 20× faster SQL parser

DBAL parses every SQL statement that has parameters to find positional and
named placeholders. For wide `SELECT` statements, such as the ones the ORM
generates for entities with many columns, this parser showed up in profiles
more than it should.

[Toon van Doorn](https://github.com/ToonvanDoornShopwoks) proposed batching the
regular expression matching of tokens, which we refined during the hackathon
([#7596](https://github.com/doctrine/dbal/pull/7596)). The number of
`preg_match()` calls drops drastically, for example from 614 to 13 for a
100-column `SELECT`:

| Statement | Before | After | Speedup |
|---|---:|---:|---:|
| Primary-key lookup | 2.8 µs | 0.8 µs | 3.4× |
| 20-column SELECT | 32.4 µs | 2.3 µs | 14.0× |
| 100-column SELECT | 145.2 µs | 8.3 µs | 17.5× |
| 400-column SELECT | 582.1 µs | 29.7 µs | 19.6× |
| INSERT, 5,000 rows, 20,000 parameters | 9.46 ms | 6.70 ms | 1.4× |

These numbers were measured with the PCRE JIT enabled, which is the PHP
default. Without the JIT the gains are still 2–5×. As a bonus, the parser now
handles very large comments and identifiers that could previously fail with a
"Backtrack limit exhausted" error.

## SQL comments in the QueryBuilder

The `QueryBuilder` has a new `addComment()` method that puts SQL comments in
front of the generated query ([#7345](https://github.com/doctrine/dbal/pull/7345)).
They show up in slow query logs and database monitoring tools, which makes it
much easier to find out where a query comes from:

```php
<?php

$queryBuilder
    ->select('id', 'name')
    ->from('users')
    ->addComment('UserRepository::findActive');

// -- UserRepository::findActive
//
// SELECT id, name FROM users
```

Comments are rendered with the `--` syntax on each line, so nothing the
comment contains can end up in the query as SQL. Keep in mind that comments
are part of the SQL string: a comment that changes on every execution, such as
a request id, defeats the result cache and prepared statement reuse.

## Moving towards immutable date and time types

DBAL has two implementations of every date and time type, one for `DateTime`
and one for `DateTimeImmutable`. Mutable dates are a common source of bugs,
especially with the ORM: a date modified in place is not detected as a change
and is silently not saved.

DBAL 4.6 takes two steps towards immutable dates:

- The mutable types `date`, `datetime`, `datetimetz`, `time` and their
  variants are deprecated ([#7575](https://github.com/doctrine/dbal/pull/7575)).
  Switch your columns to the `*_immutable` types to silence the deprecation.
  If you need to keep working with `DateTime`, the
  [UPGRADE.md](https://github.com/doctrine/dbal/blob/4.6.x/UPGRADE.md) shows
  how to write a small type that adapts the immutable one.
- Schema introspection now maps date and time columns to the immutable types
  ([#7564](https://github.com/doctrine/dbal/pull/7564)). Both variants produce
  the same DDL, so schema comparisons are not affected.

Together with ORM 3.8 no longer issuing an `UPDATE` when a new date instance
has the same database value, immutable dates are now the clear way to go.

## Supported database versions

There is a new [Supported Versions](https://www.doctrine-project.org/projects/doctrine-dbal/en/current/reference/supported-versions.html)
page in the documentation that lists the minimum database server version for
each vendor in 4.x and the planned minimums for DBAL 5.0
([#7581](https://github.com/doctrine/dbal/pull/7581)). Many versions have
reached their end of life since DBAL 4.0, so 5.0 will require MySQL 8.4,
MariaDB 10.11, PostgreSQL 15 and Oracle 19c.

Support for MariaDB 10.6 to 10.10 and MySQL 8.0 to 8.3 is deprecated now, so
it is a good time to plan your database upgrades.
